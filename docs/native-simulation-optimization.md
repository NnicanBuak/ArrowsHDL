# Оптимизация нативной симуляции: аудит 13 октября 2026

**Основной резерв сейчас — подготовка графа и повторная работа вокруг него.**
Сжатие прямых линий тоже перспективно, но должно сохранять физическую задержку
и импульсы. Замена линии переходом за один такт меняет поведение схемы.

## Критерии качества

- Сохраняются значения выходов и наблюдаемых клеток на исходных игровых тактах.
- Сохраняются импульсы, блокировки, обратные связи и последовательные состояния.
- Для RANDOM сохраняются seed и порядок расходования общего генератора.
- Время подготовки измеряется отдельно от времени нативного процесса.
- Измеренный эффект отделяется от предполагаемого; эксперименты воспроизводимы.

## Как устроено сейчас

1. `src/arrowshdl/simulation.py:31` сериализует физические клетки и сценарий,
   запускает Node.js, затем отдельный Rust-процесс.
2. `tools/compile-graph.ts:9` создаёт узел на каждую клетку, индекс координат,
   прямые и обратные связи. Учитываются вращения, разветвители, блокираторы
   и отдельные зависимости детекторов.
3. `tools/compile-graph.ts:40` запускает браузерный алгоритм поиска/валидации
   колец через синхронный адаптер. Часть подходящих PATH/XOR-колец получает
   упакованное битовое состояние и смещения относительно номера такта.
4. `native/src/main.rs:210` загружает граф через интерфейс обновления отдельных
   узлов, строит кольца и сбрасывает динамическое состояние.
5. `native/src/main.rs:260` перебирает все такты. Входы проверяются каждый такт;
   выходы считываются только на границах `hold_ticks` или `frame_ticks`.
6. `vendor/graphdlc/core/src/state.rs:201` распространяет изменения двумя фазами:
   сначала изменяет счётчики соседей, затем вычисляет новое состояние узлов.
   Очереди изменений исключают повторный обход всей карты на каждом такте.

**Рендера здесь уже нет.** Остались операции пометки визуальных чанков как
изменившихся, но нет основания считать их главным источником затрат.

`hold_ticks` сжимает сценарий и вывод отчёта, а не число вычисляемых тактов.
Состояние сохраняется между образцами одного сценария; новый вызов `simulate`
заново строит граф и запускает процесс. `run_vector_batches` повторяет это для
каждого пакета векторов.

## Что измерено

Данные: `build/native-graph-benchmark.json`. Медианы пяти запусков на текущей
Windows-машине; Rust собран в release. Время подготовки включает запуск Node,
разбор запроса, построение и сериализацию графа, передачу результата и разбор
результата в Python. При исчерпании бюджета включён повторный запуск без колец.
Сериализация первоначального запроса в Python в это время не включена.

Экспериментальный компилятор сначала удаляет из кандидатов PATH/XOR-узлы
без входов или выходов, повторяя удаление до стабилизации. Настоящие кольца
сохраняются. Это консервативное отсечение за O(V+E), а не полная декомпозиция
на сильно связанные компоненты: перемычки между кольцами могут остаться.

| Карта | Узлов | Подготовка сейчас | С отсечением | Ускорение подготовки |
| --- | ---: | ---: | ---: | ---: |
| Линия 4096, стабильный вход | 4098 | 387 мс | 51 мс | 7,5× |
| Линия 4096, вход меняется каждые 4 такта | 4098 | 379 мс | 53 мс | 7,2× |
| Линия 256 и 10 000 неиспользуемых стрелок | 10258 | 562 мс | 66 мс | 8,5× |
| ALU Workbench | 4671 | 76 мс | 53 мс | 1,4× |
| Packet Router | 3427 | 65 мс | 50 мс | 1,3× |
| Pulse Sequencer | 3098 | 61 мс | 49 мс | 1,3× |
| Minesweeper | 233969 | 1434 мс | 726 мс | 2,0× |

Линии 4096, карта с неиспользуемой линией и Minesweeper в исходном режиме
исчерпывают бюджет поиска колец. После отсечения повторный запуск не нужен.
На всех 11 измеренных случаях **узлы, связи и описания колец совпали полностью**.
Таким образом, ускоряется подготовка, а не исполнение другого графа.

Нативный процесс, включая запуск, разбор JSON, загрузку и отчёт:

| Нагрузка | Тактов | Время исходного нативного процесса |
| --- | ---: | ---: |
| Линия 256, 1 стабильный вход | 1000000 | 15 мс |
| Та же линия и ещё 128 независимых стабильных входов | 1000000 | 118 мс |
| Линия 4096, стабильный вход | 1000000 | 15 мс |
| Линия 4096, переключение каждые 4 такта | 20000 | 114 мс |
| Minesweeper без внешних воздействий | 4096 | 141 мс |
| Minesweeper, только первый такт | 1 | 134 мс |

Граф Minesweeper занимает **49,5 МБ JSON**. Близость времени одного и 4096
тактов показывает, что в данном сценарии основная нативная стоимость связана
с запуском и загрузкой. Замеры не разделяют парсинг JSON и создание узлов.
Различия времени исполнения одинаковых графов в двух режимах — шум измерений,
а не эффект предварительного отсечения.

**Ограничение:** сохранения примеров запускались с собственными внутренними
источниками, без интерактивных воздействий, с одним наблюдаемым выходом.
Это замер инфраструктурных затрат, а не проверка игровых сценариев проектов.
Часто переключающаяся синтетическая линия отдельно показывает нагрузку
при большом числе одновременно распространяющихся изменений.

## Порядок внедрения

### 1. Отсечь заведомо нециклическую часть перед поиском колец

Причина: `CycleSearchTask` начинает DFS от множества кандидатов и сбрасывает
путь после каждого корня. На линии длины N повторно обходятся её суффиксы:
затраты квадратичные, хотя результат — отсутствие колец. На графах с ветвлениями
перебор простых путей может быть ещё дороже.

Внести предварительное отсечение в локальный адаптер `tools/compile-graph.ts`,
сохранив оригинальную валидацию GraphDLC. Затем пересобрать runtime через
`tools/build.mjs`. Прототип уже находится в измерительном скрипте и работает
только с временной копией runtime. **Рабочий компилятор пока не изменён.**

Дальнейший вариант: искать только внутри сильно связанных компонент.
Не следует без доказательства заменять существующий поиск одним DFS:
перекрытия колец участвуют в правилах их допустимости.

### 2. Обновлять внешние входы только при смене образца

В `native/src/main.rs:261` значения `values[sample]` перечитываются для всех
входов на каждом такте. При `hold_ticks=1000000` образец один, но проверок
миллион на каждый вход. Входы следует применять при первом такте и при
изменении `sample`, сохраняя сравнение с предыдущим значением и те же дельты.

При одном образце число проверок падает с ticks×inputs до inputs.
При `hold_ticks=1` выигрыш практически исчезает. Прототип и измерение
ускорения этого изменения ещё не выполнены; таблица показывает текущую цену.

### 3. Повторно использовать неизменный граф

Сначала кешировать результат компиляции по хешу карты, версии компилятора и
режиму колец. Для серии сценариев лучше загружать граф в постоянный нативный
процесс один раз и отдельно сбрасывать состояние и RNG перед каждым сценарием.
Это убирает повторные Node-процессы, большой JSON и загрузку графа в каждом пакете.

Добавить путь первоначальной пакетной загрузки вместо `update_node_state` для
каждого узла: сейчас интерфейс интерактивного редактирования пересчитывает
состояния узла и соседей, после чего `reset_export` очищает эти состояния.
Сам эффект пакетной загрузки нужно измерить отдельно.

Индекс координат в Rust также устранит O(ports×nodes) линейных поисков
`position` при привязке входов/выходов/наблюдений. Протокол должен сохранять
нынешние ошибки отсутствующих и дублирующихся портов.

Глобальное изменяемое состояние GraphDLC допускает один активный расчёт
на процесс. Независимые workers могут использовать отдельные процессы.

### 4. Сжимать прямые линии в связи с задержкой

Например, связь `источник → 100 обычных стрелок → приёмник` можно представить
как доставку изменения приёмнику через **101 игровой такт после изменения
источника**. Событие хранит время доставки и дельту сигнала; промежуточные
клетки больше не требуют отдельных обновлений.

Первый безопасный вариант допускает только PATH-узлы с одним обычным входом
и одним выходом, без блокировок, детекторов, портов, наблюдений и участия
в оптимизированных кольцах. Все настоящие логические узлы остаются границами.
Замкнутые линии без границ нужно распознавать отдельно, а не считать цепочками.

Нужна очередь событий: просто добавить длину ребру в текущем движке
недостаточно — он всё равно обновляет соседей на следующем такте. Несколько
импульсов могут одновременно находиться в одной линии, поэтому хранение
только последнего значения неверно. События одного времени применяются
совместно перед вычислением следующего состояния узлов, сохраняя две фазы.

На длинных активных линиях работа может сокращаться с длина×переходы
до числа доставленных переходов плюс цена очереди. Измеренного ускорения
этого нового исполнительного механизма пока нет.

### 5. Считать только зависимости нужных выходов

Строить обратный обход от `expect`, `observe`, проверок и проб, сохраняя все
влияющие сигнальные и блокирующие связи, детекторы и состояния обратной связи.
Нельзя вырезать только по обычным геометрическим связям или ориентироваться
исключительно на достижимость от тестовых входов: есть внутренние источники.

Отдельная проблема — общий RNG. Удаление невидимого RANDOM меняет порядок
случайных чисел и может изменить видимый выход. Для совместимости такие узлы
и их причины активации нужно сохранять либо обосновывать эквивалентность.
При последующем сжатии цепей кеш должен учитывать набор наблюдений.

### 6. Пропускать пустые такты и убрать обслуживание чанков

Когда обе очереди изменений пусты, можно переходить к следующей смене входов
или моменту наблюдения. При активных read/write-головках кольца, задержках,
генераторах и RANDOM нельзя определять покой только по стабильным выходам.
Даже при отсутствии вычислений номер такта нужно корректно продвигать:
от него зависит чтение упакованного кольца.

Пустой миллион тактов с одним входом уже стоит единицы миллисекунд сверх
загрузки, поэтому это ниже по приоритету, чем исправление входного цикла.
Удаление dirty-chunk-операций разумно для отдельного headless-пути, но требует
собственного замера. SIMD и многопоточность пока не оправданы измерениями.

## Проверка и воспроизведение

```powershell
cargo build --release --locked --manifest-path native/Cargo.toml
python tools/benchmark_native_graph.py --repeat 5 --maps examples/alu_workbench/build/alu_workbench.save.txt examples/packet_router/build/packet_router.save.txt examples/pulse_sequencer/build/pulse_sequencer.save.txt examples/minesweeper/build/minesweeper.save.txt --output build/native-graph-benchmark.json
python -m unittest tests.test_simulator tests.test_reusable_backend -q
```

Прототип предварительного отсечения проверен на **19 сценариях по 120 тактов**:
кольца с записью, очисткой и XOR, четыре случайные сетки, отдельные элементы.
В обоих режимах значения **каждой клетки на каждом такте** совпали с независимым
координатным oracle из `tests/test_simulator.py`. В измеренных 11 случаях также
совпали сформированные графы и наблюдения. **16 существующих тестов прошли.**

Критерии выполнены для исследования и прототипа поиска колец. Пункты 2–6
остаются предложениями, а не проверенными изменениями исполнительного движка.
Перед сжатием линий нужны дополнительные проверки коротких перекрывающихся
импульсов, слияний, блокировки внутри пути, промежуточных наблюдений и RANDOM.
